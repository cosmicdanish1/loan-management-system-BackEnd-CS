# Ambiguities and spec discrepancies found while implementing section 44

Each item: what the spec says, what the runner does, and who should confirm. Items 1-3 changed behaviour against a literal reading.

## Discrepancies with the data
1. **Blank PFLAG: spec says 6, legacy has 9.** Section 32 lists 6 A-heads (`A1048`, `A1050`-`A1054`). The dump also has blank PFLAG on `L1046`, `L1047`, `L1048` (liabilities, `OP_BAL` 0, 9 ledger rows). The test database has the same 3 blank (the section 32 comparison found them identical). The step 2 check "no blank PFLAG remains" cannot be literal. **Runner:** blank on an A-head -> `A` (reported); blank on a credit-normal head (L, I, R, M) is left blank (blank already means credit-normal in the app, so the sign is right) and reported INFO; blank on an **E-head** is undecided and blocks. Confirm.
2. **`member_balances` cannot tie to the GL by member totals.** On the dump, head L1004 carries **+4,27,44,542 under MBNO 0 (15 rows)** and +3,08,621 under members with no record, L1001 +60,100 / +100. The section 19.5 wording "totals within the agreed tolerance of the GL" is therefore not checkable member-total vs head. **Runner:** (a) residual must be 0 (derived total = opening + ledger movement of the loaded population, proves the load), (b) the opening gap of all `fundsmaster` rows vs the head's `OP_BAL` must be within a tolerance (default **Rs 5,00,000**, option `--gl-tolerance`; the dump has 1,19,248 CD and 2,75,845 shares, matching the spec), (c) the movement that belongs to no member row is a WARN report line. **The tolerance number was never given in the spec: please confirm.** Also worth a society look: 4.27 crore of CD credit posted to member 0.
3. **"599 loans that exist only in the history table" are 599 history rows** (504 distinct (member, type, case), 118 by member + case). Reported as rows.

## Spec text that needed a decision
4. Step 1 says "exact copy, insert missing only" but those 11 tables have no key. **Runner:** insert-only into an empty table, refuse if the table already has rows (same as every other table). `headmaster` is the one "insert missing by code" table.
5. **Empty-target guard scope.** "Every data table is empty" needs a definition: a table counts as configuration only if it is in `spec.CONFIG_TABLES` (the 15 tables of 43.2 group 4); any other table with rows refuses the run (`headmaster` may hold only `I1013`, `I1014`). If the template legitimately keeps another configuration table, add it to the list.
6. **Transaction scope.** Not specified. Steps 1-13 run in one transaction (rollback leaves the template empty and re-runnable); Phase 2 and the suite run after the commit.
7. **Migrations list "equals the shipped code".** Compared as the set of timestamps in `src/migrations/*.ts` against `migrations.timestamp`. The test database lists 6 rows against 40 files (migrations were applied by one-off scripts), so this check will fail on a template built that way. Needs the template builder's convention.
8. **busrules go-live row.** Spec: "copy of SRNO 4032 with the society's values". **Runner:** copy of the row with the greatest (`APPDATE`, `SRNO`) (4032 on the dump; the tie on 19-Nov-2025 is reported), `SRNO` = max + 1 (4033), `APPDATE` = go-live date 00:00. Not specified: the new SRNO, the time part, and whether go-live must equal the open working day (checked, non-blocking, Q62). Values file: 11 keys, numeric >= 0, divisors > 0 (my addition).
9. **`member_balances` rows for members without a legacy row (914 on the dump).** Spec: identity from `member_master`. **Runner:** `SrNo` NULL, `PFNo` only if numeric (column is float), name = `full_name`, every amount column the app increments = 0 (a NULL would stay NULL after `col = col + x`), rates NULL. Copied legacy rows keep all other columns; duplicates of `MbNo` in the legacy snapshot keep the first and are reported.
10. **`share_monthly_balance`.** "Every member and every month-end from Nov 2019 to the last loaded month": **runner** includes a member from Nov 2019 onwards if it ever held shares (non-zero opening or any L1001 entry), including months with balance 0; movements dated before Nov 2019 (the 8 rows of 31-Mar-2019) are part of the opening position; `snapshot_date` is the calendar month-end (also for the current month, which is partial); population = the `member_balances` population so the last month ties to `member_balances.Shares`.
11. **`tblcashbook`.** Opening row: `headcode` `A1001`, `headname` "OPENING BALANCE 31-10-2019" (not specified), cash and transfer in one row. Rows from 01-Nov-2019 (the 8 rows of 31-Mar-2019 are excluded); `MODEOFPAY` NULL counts as transfer; `voucher_no`, `voucher_id`, `username` empty. "First live day" is the day after the last ledger date; its opening = sum of all rows = ledger cash in hand and transfer 0.
12. **Counters.** `MEMBER_NO` is raised to the highest member number (990042381 on the dump) although the app pads it as an 8-digit number: confirm that is the intended scheme. `LOAN_CASE` to the highest of `loan_master`/`loan_pending`; `VOUCHER_NO` only if a `VCH` number exists in the ledger. `REAGREEMENT_NO` and unknown keys are not touched. A missing key (`LOAN_CASE`, `MEMBER_NO`, `VOUCHER_NO`) in the template fails the run rather than inserting one.
13. **`full_name`.** "Trimmed, single spaces": runner joins the non-empty parts with one space (the old script used `trim(concat_ws(' ', ...))`, which leaves a double space when a middle name is blank).
14. **`member_master` hash.** The SHA-256 is taken after emulating the retirement trigger (`dor` := `date_of_retirement`), over the 42 legacy columns plus `full_name` and `cast_category`; the raw legacy baseline hash is separate. The trigger must be present and enabled (pre-flight).
15. **Phase 2 hook.** The existing script is hard-wired to `localhost:5432 / EMP_Espat_Society / postgres` and legacy `EMP_Espat_Society_dan`; the hook refuses any other target/legacy name (no change to `src/`). The blocking outcomes are read from `legacy_replay_batch_log` (`status = 'failed'`, `flags::text` containing the two flag names; the column type of `flags` was not checked). Loan heads for the per-member check: RLN -> A1002, ALN/ELN -> A1047 (read from the replay script), tolerance Rs 50 (the script's own), reported but not blocking (Q55 blocks only the three outcomes).
16. **Report lines whose predicate the spec did not define** (defined by me, each reproduces the dump reference count): incomplete cheque rows, "never passed" demand rows, junk sanction, rows that "do not add up" in `loan_balance_history`, ACC_TYPE vs head code, repeated pairs. **Not implemented** (predicate unknown): the 23 name differences between `frs` and `member_master` (section 18) and the 2 repeated pairs of `loan_product`; the `TotalDemand` vs parts check of 249 rows (needs the list of part columns). `membercategory` duplicates are counted as groups (11).
17. **Freeze check.** "No session on the legacy database" blocks only in `--execute`; in dry run it is a NOTE (the dump currently shows another session).
18. **Smoke test through the app** (44.3) is a manual checklist line in the report, not automated.
19. `--steps` is accepted only for dry runs: a real load always runs steps 1-13 together.
20. **Location.** `backend/` is a separate git repository from the root repo; the runner lives in the new folder `backend/scripts/legacy-migration/runner/` and nothing was committed.
